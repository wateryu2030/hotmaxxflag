## 一、目标与原则

### 1.1 业务目标（专家意见内化）

1. **分析可信**：同一决策场景下，销售额、毛利、毛利率的**数据来源与粒度**可解释，避免「洞察一套数、人力页另一套数」。  
2. **品类可下钻**：从大类到中类（必要时小类）能连贯看**结构、毛利、与人力的匹配度**，而不是只停在汇总或单次报告。  
3. **人力可对账**：类目–岗位映射**有覆盖率与变更审计**，未映射、跨月规则变化可被发现。  
4. **从指标到动作**：在现有洞察与营销报告之上，增加少量**固定模板**（如四象限、投入产出排行），减少每次人工解读成本。

### 1.2 技术原则

- **优先用现有表**：在补充订单号/客流之前，不承诺连带率、提袋率等（见可行性文档）。  
- **控制 `app.py` 体积**：新能力优先拆到独立模块并在 `app.py` 注册路由（与《项目重构与优化方案》一致）。  
- **API 与看板同步**：新指标先定义 JSON 契约与口径说明，再落前端，避免「有数无释」。

## 二、现状基线（摘要）

| 领域 | 已有能力 | 主要缺口 |
|------|----------|----------|
| 销售与 KPI | `t_htma_sale` 聚合、趋势、KPI、消费洞察矩阵 | 部分洞察仍依赖 `t_htma_profit`，与人力/明细需**口径对齐** |
| 品类与毛利 | 大类/中类/小类排行、饼图、营销报告、`analytics` 洞察 | **中类 × 人力**在配置中有、主分析路径可再强化；贡献结构可产品化 |
| 人力与人效 | `labor_analysis`、映射表、按大类分摊成本与毛利/销售比 | **管理人力与经营类目**叙事、映射覆盖率告警、表头增加「人力占销/占毛利」等 |
| 税务/发票/红背篓/飞书 | 近期已合入主干 | 与核心经营看板的**入口与权限**需持续统一 |
| 工程 | 单仓脚本与 OpenClaw 校验 | 自动化测试薄弱、`app.py` 过大 |

## 三、分阶段路线图

建议以 **6～8 周为一轮**，每轮交付可演示的「业务可感知」增量；下列阶段可重叠，但**阶段 A 应最先闭环**。

### 阶段 A：可信与一致（约 2～3 周）— P0

**目的**：专家意见中最影响信任的一条——**毛利/品类口径统一**。

| 工作项 | 产出 | 验收要点 |
|--------|------|----------|
| 定义「经营分析主口径」 | 简短说明（可放在 `docs/` 或 API 注释）：默认以 `t_htma_sale` 聚合为准 | 人力分析、品类排行、趋势、新增卡片**同一筛选下毛利一致** |
| 洞察与 `t_htma_profit` | 要么改为从 `t_htma_sale` 聚合，要么明确为「日品类汇总表视角」并在 UI 标注 | 与人力页对比时无歧义 |
| 人力分析表增强 | 大类行增加：毛利率、人力成本/销售额、人力成本/毛利（或与现有 `profit_cost_ratio` 并列展示） | 业务可一眼回答「薪酬相对毛利重不重」 |
| 映射健康度 | 「有大类销售但经营映射为空」的列表或计数 | 避免将「未分摊人力」误读为高人效 |

### 阶段 B：品类 × 毛利 × 人力深度（约 3～4 周）— P1

**目的**：把专家建议的「对比薪酬后如何提升」落到**固定分析模板**。

| 工作项 | 产出 | 验收要点 |
|--------|------|----------|
| 贡献结构视图 | 各大类：销售额占比 vs 毛利占比（条形或并列指标） | 识别「卖得多但赚得少」的品类 |
| 四象限或评分卡（简版） | 横轴毛利率或毛利贡献，纵轴人力强度（如人力/毛利） | 输出可解释的象限标签（控本/提价/结构优化等） |
| 中类下钻（销售侧） | 选定大类后，中类销售+毛利+毛利率表（可与现有 API 组合或扩展） | 与人力大类对齐后的**二级叙事** |
| 管理人力说明 | 文档 + 看板脚注：管理成本是否参与大类拆分；若做「全店分摊参考」需标注假设 | 汇报时口径统一 |

### 阶段 C：经营扩展包（持续滚动）— P2

**目的**：落实《现有数据还能做哪些经营性分析》中**高价值、低依赖**项，并与品类/毛利联动。

建议默认顺序（可按业务调整）：

1. **退货与赠送**占比（按大类/品类）— 与毛利异常排查联动  
2. **品牌/供应商**贡献与毛利率— 与采购、清场决策联动  
3. **负毛利明细** + 导出— 与阶段 A 洞察互补  
4. **价格带 / 件单价**— 与结构优化、促销选品联动  
5. **SKU 周转与 ABC**— 与库存预警、陈列资源联动  
6. **品类结构随时间变化**— 与季节性与资源倾斜联动  
7. **数据质量看板扩展**（成本/品类一致性）— 保障以上分析可信  

### 阶段 D：工程与可持续交付（与 B/C 并行）

| 工作项 | 说明 |
|--------|------|
| 拆分 `app.py` | 按域拆路由模块（人力、销售、导入、税务等），控制单文件行数 |
| 关键 API 契约 | 对 `/api/labor_analysis/*`、核心 KPI/品类接口维护请求/响应示例或轻量 OpenAPI |
| 自动化 | 对纯计算与 SQL 组装层增加单元测试；保留 OpenClaw 脚本做冒烟 |
| 配置与密钥 | `.env.example` 与生产配置分离；飞书/数据库密钥不入库 |

## 五、风险、依赖与不做清单

**风险**

- 人力为**按月**、销售为**按日**；跨月映射变更会导致历史对比波动，需在变更时保留 `effective_from` / `effective_to` 并做说明。  
- 品类字段在日报中若不稳定，会放大「品类一致性」问题，需导入侧校验（阶段 C 数据质量项）。

**依赖**

- 类目–人力映射需业务方**月度核对**（岗位改名、新店、架构调整）。  

**本轮明确不做（除非业务补数）**

- 依赖订单号/小票的连带率、客单价分布（按单）、提袋率等（见可行性文档）。

## 六、小结

本计划将专家建议收敛为：**先口径与映射可信（A），再品类×毛利×人力模板化（B），再按已有数据清单扩展经营分析（C），工程化并行（D）**。  
每轮迭代结束建议做一次**短回顾**：本周是否减少了「同一问题两套数」的争议，以及是否多了一条可执行的品类或人力动作。
